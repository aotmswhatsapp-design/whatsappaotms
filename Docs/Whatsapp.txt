# PRODUCT REQUIREMENTS DOCUMENT (PRD)
# Managed WhatsApp Automation SaaS

**Version:** 5.0  
**Product Type:** Centrally Managed WhatsApp Automation SaaS  
**Business Model:** Subscription-Based Software Access  
**Deployment Model:** One Central Application, Isolated Database Per Customer  
**Architecture:** Shared Codebase, Centralized Infrastructure, Independent Customer Databases  
**Automation:** Custom Backend (No n8n)

---

# 1. PRODUCT OVERVIEW

## 1.1 Product Vision

Build a subscription-based WhatsApp Automation SaaS platform that allows customers to purchase access through the company's website and automatically receive their own isolated WhatsApp Automation workspace after successful payment.

The software will be developed, hosted, maintained, and controlled by our company.

Customers purchase software access, not source code or a separate software deployment.

## 1.2 Business Model

Our company owns and manages:

- Source code and Git repository.
- Frontend and backend applications.
- Hosting infrastructure.
- Database infrastructure.
- Customer account provisioning.
- Application updates and maintenance.
- Security and monitoring.
- Subscription and billing operations.
- Backup and recovery systems.

Customers receive:

- Login access to their own workspace.
- Access to the features included in their subscription plan.
- Their own isolated PostgreSQL database.
- Their own WhatsApp Business account integration.
- Their own contacts, messages, campaigns, automations, and reports.
- Customer-specific usage and subscription information.

Customers do not receive source code, backend access, database server credentials, or deployment infrastructure access.

## 1.3 Core Product Concept

**One Company Website → Customer Payment → Automatic Account Creation → Separate Customer Database → Workspace Access → WhatsApp Automation.**

All customers use the same application, branding, UI, theme, and feature design.

Only customer data, WhatsApp configuration, subscription details, and workspace information are different.

## 1.4 Product Objectives

1. Build a complete WhatsApp Automation SaaS platform.
2. Sell subscriptions through our company landing page.
3. Automate customer onboarding after verified payment.
4. Create an independent PostgreSQL database for every customer.
5. Maintain one common source code repository.
6. Operate one centrally managed application.
7. Keep all source code and infrastructure under company control.
8. Support independent WhatsApp Business accounts for customers.
9. Implement subscription expiry and renewal management.
10. Eliminate n8n dependency.
11. Support automated provisioning, backups, and maintenance.
12. Scale customer onboarding without manually deploying separate projects.

5. Create the customer account.

If provisioning fails after payment, the system must retry safely or alert internal operations staff.

A failed provisioning operation must not create duplicate customers, databases, or subscriptions.

# 5. AUTHENTICATION AND USER MANAGEMENT

## 5.1 Authentication Architecture

Authentication will be implemented using NestJS and the customer's own PostgreSQL database.

Technologies:

- NestJS Authentication Module.
- Prisma ORM.
- Argon2id password hashing.
- JWT access tokens.
- Rotating refresh tokens.
- Email verification.
- Password reset.
- Role-based access control.

## 5.2 Authentication Features

- Account activation.
- Login.
- Logout.
- Logout from all sessions.
- Email verification.
- Password reset.
- Password change.
- Session management.
- Refresh-token rotation.
- Refresh-token revocation.
- Profile management.
- Role-based permissions.

## 5.3 Security Requirements

- Access tokens must have a short expiry.
- Refresh tokens must be rotated and stored securely.
- Store refresh-token hashes rather than raw tokens.
- Passwords must be hashed using Argon2id.
- Verification and reset tokens must be single-use and expire.
- Login and password-reset endpoints must be rate-limited.
- Authentication events must be logged.
- Sensitive operations must require authorization checks.
- Customer sessions must be bound to the correct workspace.

The application must never trust a customer-supplied workspace ID without verifying the authenticated user's membership.

- Email delivery.
- Payment gateway integration.
- WhatsApp integration services.

## 7.3 Customer Database Isolation

Every customer receives a separate PostgreSQL database.

Example:

**Customer A**
- Customer ID: CUST_A
- Database: customer_a_db
- Database credentials: Customer A-specific credentials
- WhatsApp credentials: Customer A-specific credentials
- Subscription: Customer A subscription

**Customer B**
- Customer ID: CUST_B
- Database: customer_b_db
- Database credentials: Customer B-specific credentials
- WhatsApp credentials: Customer B-specific credentials
- Subscription: Customer B subscription

Both customers use the same application and backend code.

## 7.4 Database Connection Management

The backend must:

1. Authenticate the user.
2. Resolve the user's authorized workspace.
3. Retrieve the database mapping from the protected control-plane registry.
4. Obtain the corresponding database credentials from secure secret storage.
5. Establish or reuse a safe database connection.
6. Execute operations only against the authorized customer's database.
7. Release or reuse connections safely.

Never accept arbitrary database URLs from customer requests.

Connection pooling and maximum connection limits must be designed for high customer counts.

# 10. DATABASE PROVISIONING SERVICE

## 10.1 Provisioning Responsibilities

The provisioning service must:

- Generate a unique customer identifier.
- Generate a unique workspace identifier.
- Allocate a database name.
- Create a separate PostgreSQL database.
- Create restricted database credentials.
- Apply schema migrations.
- Initialize required default records.
- Register the database mapping.
- Create the initial owner account.
- Activate the workspace.
- Record provisioning results.

## 10.2 Provisioning Reliability

The provisioning system must support:

- Idempotent operations.
- Retry handling.
- Provisioning timeouts.
- Failed-job recovery.
- Duplicate event prevention.
- Database creation verification.
- Migration verification.
- Operational alerts.
- Provisioning audit logs.

If a customer pays successfully but database provisioning fails, the payment record must remain valid and the provisioning operation must be recoverable.

## 10.3 Database Lifecycle

When a subscription expires:

- Apply the configured grace period.
- Restrict access according to the subscription policy.
- Preserve customer data according to the retention policy.
- Notify the customer about renewal.
- Restore normal access after successful renewal.

When a customer permanently cancels:

- Apply the documented cancellation policy.
- Allow data export where applicable.
- Retain or delete data according to the retention and legal policy.
- Revoke database credentials when deletion is authorized.
- Record the lifecycle action in audit logs.

Never automatically delete customer databases immediately after subscription expiry.

# 17. FINAL PRODUCT DEFINITION

The final product is a centrally managed, subscription-based WhatsApp Automation SaaS platform.

Our company owns and manages the source code, application, hosting infrastructure, backend, database infrastructure, security, maintenance, and software updates.

Customers purchase access through our public website. After verified payment, the system automatically creates their account, provisions a separate PostgreSQL database, initializes their workspace, and delivers login instructions.

Each customer uses the same application and company branding but has independently isolated business data, users, WhatsApp credentials, subscription, and workspace.
